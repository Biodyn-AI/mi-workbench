\section*{Abstract}
Mechanistic interpretability (MI) of biological foundation models---such as single-cell transformers trained on gene expression data---requires iterative cycles of hypothesis formation, experimental execution, statistical evaluation, and adversarial critique. These cycles are labor-intensive, error-prone, and difficult to reproduce. We present MI-Workbench, an open-source platform that coordinates a team of large language model (LLM) agents through a single, inspectable orchestrator to carry out MI investigations. Workflows are declared in a graph-based domain-specific language (DSL) whose nodes are agent roles---executor, a configurable panel of reviewer lenses (rigour, adversarial, biological plausibility), idea generator, and knowledge extractor---and each agent is reached through a provider-agnostic adapter layer supporting Claude Code, OpenAI Codex, and Google Gemini. Key mechanisms include: (i)~a consensus reviewer that runs a reviewer panel concurrently and merges their critiques by Jaccard deduplication with agreement-based severity escalation and an optional advancement gate; (ii)~structured, artifact-aware feedback that maps critiques to specific artifacts and sections for targeted revision; (iii)~optional sandboxed execution of the analysis code an agent emits, so reviewers critique executed results rather than an untested plan; and (iv)~an output-cleaning pipeline, automated convergence detection, and reproducibility packaging. We characterise the orchestrator with deterministic ablation and load experiments---larger reviewer panels surface strictly more distinct, complementary critiques, and the coordinator sustains concurrent runs with graceful tail-latency growth---and corroborate the panel with a live Gemini backend. A case study on whether Geneformer attention heads encode causal gene regulation shows the platform identifying key confounders (co-expression bias, rank-value encoding artifacts, attention symmetry) and refining analyses through structured feedback without human intervention. The system comprises roughly 9{,}200 lines of backend Python with an accompanying suite of over 370 tests, and supports real-time monitoring via WebSocket streaming.

\section*{Introduction}
The rapid development of biological foundation models---including scGPT~\cite{cui2024scgpt}, Geneformer~\cite{theodoris2023transfer}, and scBERT~\cite{yang2022scbert}---has raised fundamental questions about what these models learn and how their internal representations relate to known biology. Mechanistic interpretability (MI), the discipline of reverse-engineering the computational mechanisms within neural networks~\cite{olah2020zoom,elhage2022toy,conmy2023towards}, offers a principled framework for answering these questions. However, applying MI to biological models presents unique challenges:

\begin{enumerate}
  \item \textbf{Confounding structures.} Gene co-expression, regulatory network degree distributions, and expression magnitude biases create complex confound structures that require carefully controlled null models~\cite{pratapa2020benchmarking}.
  \item \textbf{Statistical rigor.} Claims about learned regulatory mechanisms require multiple testing correction, effect size reporting, confidence intervals, and proper null model comparison---standards often missing from initial analyses.
  \item \textbf{Iterative refinement.} MI investigations are inherently cyclical: an initial analysis reveals confounders, which motivate new controls, which reveal subtler effects, and so on.
  \item \textbf{Reproducibility.} Complex computational pipelines with many degrees of freedom are difficult to reproduce without meticulous documentation of parameters, data versions, and analytical choices.
\end{enumerate}

While individual LLMs have demonstrated impressive capability for scientific reasoning~\cite{romera2024mathematical,boiko2023autonomous}, a single agent prompted once lacks the adversarial pressure and structured quality control that rigorous research demands. A human researcher instead cycles between the roles of executor (performing analysis), reviewer (critiquing methodology), and devil's advocate (searching for confounders and alternative explanations). MI-Workbench assigns these roles to distinct LLM agents and coordinates them.

The system is best described as an \emph{agentic orchestration platform} rather than a distributed multi-agent system in the classical sense: agents do not run autonomous, asynchronous control loops or exchange messages through an agent communication language. A single orchestrator sequences them according to an explicit workflow graph. This centralization is a deliberate design choice for scientific quality assurance---it makes every run deterministic in its control flow, inspectable, auditable, and reproducible---and it does not preclude concurrency where it matters: the reviewer panel is evaluated in parallel within an iteration. We introduce MI-Workbench, a platform that automates this multi-role research process. Our key contributions are:

\begin{itemize}
  \item A \textbf{graph-based workflow DSL} that lets researchers declare multi-role research loops with conditional execution, concurrent reviewer fan-out, and configurable stop conditions, validated before execution.
  \item A \textbf{consensus reviewer mechanism} that runs a configurable panel of critic lenses concurrently and merges their findings through deduplication, agreement-based severity escalation, deterministic ranking, and an optional advancement gate.
  \item A \textbf{structured feedback loop} that maps reviewer critiques to specific artifacts and sections, enabling targeted revision rather than wholesale rewriting.
  \item \textbf{Sandboxed verified execution} that optionally runs the analysis code an executor emits and folds the captured results back into review, so critique targets executed output rather than an untested plan.
  \item A \textbf{provider-agnostic adapter architecture} abstracting over Claude Code, OpenAI Codex, and Google Gemini CLI backends through a common interface, with an integrated \textbf{knowledge extraction} pipeline and end-to-end \textbf{reproducibility packaging}.
  \item A \textbf{quantitative evaluation} of the orchestrator---panel-size ablations, reviewer-lens complementarity, convergence behaviour, and concurrent-run load benchmarks---alongside a domain case study.
\end{itemize}

\subsection*{Related work}

\noindent\textbf{Autonomous scientific agents.} The vision of AI-driven scientific discovery has been explored through systems like ChemCrow~\cite{bran2024chemcrow}, which chains LLM reasoning with chemistry tools, and Coscientist~\cite{boiko2023autonomous}, which demonstrated autonomous experimental design in chemistry. SciAgents~\cite{ghafarollahi2024sciagents} explored multi-agent scientific reasoning using graph-based ontologies. These systems focus primarily on wet-lab experimental design; MI-Workbench targets the distinct challenge of computational interpretability with its emphasis on statistical rigor and confound control.

\noindent\textbf{Multi-agent LLM frameworks.} Multi-agent debate and collaboration have been studied in frameworks such as CAMEL~\cite{li2023camel}, AutoGen~\cite{wu2023autogen}, and ChatDev~\cite{qian2024chatdev}. MetaGPT~\cite{hong2023metagpt} introduced structured output schemas for software engineering agents. CrewAI and LangGraph provide general-purpose agent orchestration. Classical multi-agent systems emphasise autonomous agents with independent control loops that coordinate through message passing; MI-Workbench instead adopts a centrally orchestrated design in which a single engine sequences role-specialised LLM calls along an explicit graph. We make this trade-off deliberately: for automated scientific critique, a deterministic and inspectable control flow is worth more than agent autonomy, because it is what makes a run auditable and reproducible. MI-Workbench also differs from these frameworks in its domain specialization---the agent roles, prompt templates, artifact types, and quality criteria are designed for mechanistic interpretability research---while keeping the orchestration core domain-agnostic, so the same machinery drives other domains by swapping prompts.

\noindent\textbf{Mechanistic interpretability.} The MI field has produced foundational work on circuits~\cite{olah2020zoom}, induction heads~\cite{olsson2022context}, activation patching~\cite{meng2022locating}, and superposition~\cite{elhage2022toy}. Recent work has applied MI concepts to biological transformers: Geneformer~\cite{theodoris2023transfer} and scGPT~\cite{cui2024scgpt} have been probed for gene regulatory network (GRN) inference capabilities. However, these analyses are typically manual, one-shot investigations. MI-Workbench provides the infrastructure to systematize and scale such investigations.

\noindent\textbf{Scientific workflow systems.} Systems like Galaxy~\cite{afgan2018galaxy}, Nextflow~\cite{ditommaso2017nextflow}, and Snakemake~\cite{molder2021sustainable} manage computational biology pipelines. These tools orchestrate deterministic code execution; MI-Workbench orchestrates \emph{reasoning} via LLM agents, where outputs are non-deterministic and require quality assessment.

\section*{Materials and methods}

MI-Workbench follows a layered architecture (Fig~\ref{fig1}) comprising: (i)~a REST API layer built on FastAPI with WebSocket support for real-time monitoring; (ii)~an orchestration engine that drives the multi-agent loop; (iii)~a provider-agnostic adapter layer that interfaces with LLM backends; and (iv)~persistence and artifact management via SQLite and a structured file system.

\subsection*{System architecture}

The four layers follow a strict separation of concerns, each isolating one axis of change. The interface layer decouples how a run is launched (CLI, HTTP, or a monitoring socket) from what it does. The orchestration layer holds all coordination logic---graph compilation, sequencing, review merging, convergence, and follow-up generation---in one place, which is what makes control flow auditable (a single reader can follow an entire run) and is the layer this paper evaluates. The adapter layer is a deliberate anti-corruption boundary: because every backend is reached through one narrow \texttt{run}/\texttt{smoke\_test}/\texttt{is\_available} interface, the orchestration logic never depends on a vendor SDK, and new providers or a zero-cost mock are added without touching the engine. The persistence layer records every artifact, prompt, and run parameter so that any run can be reconstructed and packaged for reproduction. This is the standard layering of a service that must be simultaneously vendor-neutral and reproducible; the novelty is in the orchestration layer, not the tiering itself.

\subsubsection*{Workspace model}
A \emph{workspace} represents an isolated research context with its own configuration, provider settings, budget limits, and git integration mode. Each workspace contains one or more \emph{runs}, where each run executes a loop definition against a specific research task. Runs produce versioned \emph{artifacts} organized by iteration: mechanistic analysis (\texttt{MECH.md}), evaluation reports (\texttt{EVAL.md}), experimental protocols (\texttt{XP.md}), methodology documentation (\texttt{METHOD.md}), and knowledge summaries (\texttt{KNOWLEDGE.md}).

\subsubsection*{Data model}
The system uses Pydantic~\cite{pydantic} for all data validation and serialization. Key models include \texttt{RunState} (tracking run lifecycle, iterations, token usage, and cost), \texttt{IterationResult} (individual step outcomes with artifacts and feedback), \texttt{ReviewResult} (structured critique with severity levels and artifact references), and \texttt{LoopDefinition} (graph-based workflow specification).

\subsection*{Graph-based workflow DSL}

MI-Workbench defines research workflows as directed graphs where nodes represent agent roles and edges encode execution flow with conditions.

\subsubsection*{Loop definition}
A loop definition consists of \emph{nodes} and \emph{edges} specified in YAML:

\begin{lstlisting}
nodes:
  - id: executor
    role: executor
    prompt_ref: "executor/mi_executor"
  - id: reviewer
    role: reviewer
    prompt_ref: "reviewer/mi_reviewer"
  - id: adversarial
    role: adversarial_reviewer
    prompt_ref: "adversarial_reviewer/adversarial_reviewer"
edges:
  - source: executor
    target: reviewer
    condition: "always"
  - source: reviewer
    target: executor
    condition: "always"
  - source: reviewer
    target: adversarial
    condition: "every_k:3"
\end{lstlisting}

\subsubsection*{Edge conditions}
Three condition types are supported:
\begin{itemize}
  \item \texttt{always}: the edge is traversed every iteration.
  \item \texttt{every\_k:$N$}: the edge is traversed every $N$-th iteration (e.g., adversarial review every 3rd cycle).
  \item \texttt{on\_flag:$F$}: the edge is traversed only when flag $F$ is set (e.g., \texttt{on\_flag:high\_risk\_claims}).
\end{itemize}

\subsubsection*{Compilation}
The DSL compiler performs a topological walk of the graph, validates structural integrity (no unreachable nodes, no duplicate IDs), and produces an ordered \texttt{ExecutionPlan} with a cycle length for infinite-loop repetition. Stop conditions include budget limits (tokens, cost, iterations), convergence detection, grade thresholds, and user-initiated cancellation.

\subsubsection*{Built-in presets}
Four presets are provided:
\begin{enumerate}
  \item \textbf{executor\_reviewer}: standard executor--reviewer loop with periodic adversarial review.
  \item \textbf{reviewer\_consensus}: three parallel reviewers (standard, adversarial, biological plausibility) with consensus merger.
  \item \textbf{research\_followups}: executor--reviewer loop with automated follow-up proposal generation and optional auto-dispatch.
  \item \textbf{example\_custom}: advanced loop with conditional adversarial escalation, knowledge extraction, and graph stability detection.
\end{enumerate}

\subsection*{Multi-agent orchestration}

A single orchestrator drives every run as a synchronous loop over the compiled plan (Algorithm~\ref{alg:loop}), issuing one agent step per iteration. This centralization is what makes a run reproducible and auditable: the sequence of agent calls for a given loop and task is fully determined by the graph, and the entire control flow lives in one module a reviewer can read end to end. Concurrency is introduced deliberately and locally---within a consensus step the reviewer panel is dispatched with \texttt{asyncio.gather}, and independent runs execute as separate asynchronous tasks (up to a configured ceiling)---so the orchestrator scales across concurrent investigations without sacrificing the determinism of any single one. We quantify both properties in the Results.

\subsubsection*{Agent roles}
MI-Workbench defines nine agent roles (Table~\ref{table_roles}) that fall into four groups. The \textbf{executor} performs analysis and emits artifacts. Three \textbf{reviewer lenses}---rigour, adversarial, and biological plausibility---critique that output; they are intentionally distinct rather than redundant, each trained by its prompt on a different failure mode (statistical rigour, adversarial confounds, and domain plausibility, respectively), and we show in the Results that they surface largely non-overlapping critiques. Two \textbf{generative} roles (idea generator, automator) propose follow-up experiments and reusable pipelines, and three \textbf{dissemination and knowledge} roles (knowledge extractor, publication manager, article publisher) structure findings and mine claims. Only the executor and the reviewer lenses are required for a review loop; the remaining roles are optional nodes a workflow may include. Because roles are graph nodes rather than hard-coded stages, a workflow toggles any role by including or omitting it, and the reviewer panel is resized simply by adding or removing lens nodes.

\subsubsection*{Execution loop}
The core execution loop (Algorithm~\ref{alg:loop}) drives the iterative research process.

\begin{algorithm}[!ht]
\caption{MI-Workbench execution loop}
\label{alg:loop}
\begin{algorithmic}[1]
\Require RunState $R$, LoopDefinition $L$, Adapter $A$
\State $P \gets \textsc{Compile}(L)$ \Comment{Compile to execution plan}
\State $i \gets 0$, $\mathit{feedback} \gets \emptyset$
\While{$\neg\textsc{BudgetExceeded}(R) \wedge \neg\textsc{Converged}(R) \wedge \neg\textsc{Cancelled}(R)$}
  \State $s \gets P.\mathit{steps}[i \bmod |P|]$
  \If{$\neg\textsc{ShouldRun}(s, R.\mathit{iteration})$}
    \State $i \gets i + 1$; \textbf{continue}
  \EndIf
  \State $\mathit{prompt} \gets \textsc{BuildPrompt}(s, R, \mathit{feedback})$
  \State $\mathit{result} \gets \textsc{RunWithRetry}(A, \mathit{prompt})$
  \State $\mathit{result.output} \gets \textsc{StripTraces}(\mathit{result.output})$
  \State $\mathit{artifacts} \gets \textsc{ParseArtifacts}(\mathit{result.output}, s.\mathit{role})$
  \State $\textsc{WriteArtifacts}(\mathit{artifacts}, R.\mathit{iteration})$
  \If{$s.\mathit{role} \in \{\mathit{reviewer}, \mathit{adversarial}\}$}
    \State $\mathit{review} \gets \textsc{ParseReview}(\mathit{result.output})$
    \State $\mathit{feedback} \gets \textsc{FormatFeedback}(\mathit{review})$
  \Else
    \State $\mathit{feedback} \gets \mathit{result.output}$
  \EndIf
  \State $\textsc{RecordConvergence}(R.\mathit{iteration}, \mathit{result})$
  \State $R.\mathit{iteration} \gets R.\mathit{iteration} + 1$; $i \gets i + 1$
\EndWhile
\State \Return $R$
\end{algorithmic}
\end{algorithm}

Algorithm~\ref{alg:loop} shows the ordinary single-agent step for clarity. Two step kinds specialise it. A \emph{consensus} step (compiled from a workflow whose reviewers fan out to a merger node) replaces the single \textsc{RunWithRetry} call with a concurrent dispatch of the whole reviewer panel followed by a merge (described below). When verified execution is enabled, an executor step additionally runs the analysis code it emitted and appends the captured results to the feedback before the reviewers see it.

\subsubsection*{Stopping and iteration budget}
A run continues until the first of four conditions holds: the iteration ceiling (\texttt{max\_iterations}, default 50) is reached; the token budget (default 500{,}000) or cost budget is exceeded; convergence is detected; or the user cancels. These bounds cap the number of feedback rounds; a typical review loop converges well before the ceiling (Results).

\subsubsection*{State machine}
Run lifecycle is managed by a finite state machine with states \{Pending, Running, Paused, Stopped, Completed, Failed\} and well-defined transitions. Paused runs can be resumed with full state reconstruction from the database and artifact filesystem. A crash recovery module detects interrupted runs on server restart, transitioning Running states with existing iterations to Paused for resumability.

\subsubsection*{Convergence detection}
After a minimum of four iterations, three convergence signals are monitored over a sliding window of $w$ reviews (default $w{=}3$):
\begin{enumerate}
  \item \textbf{Grade stability}: the reviewer grade has remained constant for $w$ consecutive reviews.
  \item \textbf{Zero critical issues}: no Critical or High severity critiques for $w$ reviews.
  \item \textbf{Output similarity}: Jaccard word-level similarity between consecutive executor outputs exceeds threshold $\tau$ (default $0.9$) for $w$ iterations.
\end{enumerate}
Any single signal triggers loop termination, preventing waste of compute on converged analyses. When the consensus advancement gate is enabled, convergence is suppressed while any Critical critique remains unresolved, so the loop does not declare success over an open critical issue.

\subsubsection*{Retry logic}
Adapter calls are wrapped in exponential backoff retry with jitter. Transient errors (rate limits, timeouts, connection failures) trigger retry with delay $d_k = d_0 \cdot 2^k \cdot (1 + \epsilon)$, where $\epsilon \sim \mathcal{U}(-0.25, 0.25)$. Permanent errors (authentication failures, invalid requests) fail immediately.

\subsection*{Consensus review mechanism}

A central mechanism of MI-Workbench is the \emph{consensus reviewer}, which replaces single-reviewer assessment with a panel and a defined aggregation rule.

\subsubsection*{Panel}
The panel is a configurable list of reviewer lenses declared in the workflow graph; the default MI panel has three---rigour, adversarial, and biological plausibility---but a workflow may use fewer or more, and the lenses are domain-configurable through their prompts. Within a consensus step the panel is dispatched concurrently over the current executor artifact, so panel latency is that of the slowest lens rather than their sum.

\subsubsection*{Critique merging}
The merge operates in four phases. \textbf{Phase 1 (parsing):} each lens's free text is parsed into structured \texttt{ReviewCritique} objects using multi-format detection---bracket (\texttt{[SEVERITY] description}), Markdown (\texttt{**Severity: X** --- description}), and structured (\texttt{Severity: X, Category: Y, Description: Z}). \textbf{Phase 2 (deduplication):} critiques are grouped by Jaccard word-overlap similarity,
\begin{equation}
J(c_i, c_j) = \frac{|\mathrm{words}(c_i) \cap \mathrm{words}(c_j)|}{|\mathrm{words}(c_i) \cup \mathrm{words}(c_j)|},
\end{equation}
with pairs satisfying $J(c_i, c_j) \geq \tau$ (default $\tau{=}0.5$) merged into one group. \textbf{Phase 3 (agreement-based escalation):} each group takes the maximum severity present; if at least $k$ distinct lenses raised the group (the \emph{consensus threshold}, default $k{=}2$), its severity is escalated one level (capped at Critical), encoding the intuition that inter-lens agreement signals importance. \textbf{Phase 4 (deterministic ranking):} groups are ordered by severity, then by an optional per-role weight, then by the number of contributing lenses, with the critique text as a final tie-break so the ranking never depends on parse or dispatch order.

\subsubsection*{Consensus definition, gating, and deadlock}
``Consensus'' here is thus an explicit aggregation---dedup, agreement-weighted severity, and deterministic ranking---rather than a vote, and the loop advances every iteration by default. When stricter behaviour is wanted, an optional \emph{advancement gate} is the deadlock policy: while the merged result contains an unresolved Critical critique, the run is not allowed to converge or complete and instead keeps revising, bounded by the iteration ceiling so a genuinely irreconcilable panel terminates rather than looping forever. Ties are broken deterministically as above, so a split panel produces a stable, reproducible ordering rather than an undefined one.

\subsubsection*{Grade computation}
An overall grade is computed from the merged critique list: $\geq 2$ Critical $\Rightarrow$ F; $\geq 1$ Critical $\Rightarrow$ D; $\geq 3$ High $\Rightarrow$ D; $\geq 1$ High $\Rightarrow$ C; $\geq 1$ Medium $\Rightarrow$ B; otherwise A.

\subsection*{Structured feedback and output cleaning}

\subsubsection*{Artifact-aware feedback}
A key finding from initial deployments was that generic feedback (``Previous iteration output: \ldots Continue with: task'') produced shallow revisions. We introduced \emph{artifact-aware feedback} with two innovations. First, \textbf{reference inference}: when parsing reviewer critiques, the system infers artifact references (e.g., \texttt{PROTOCOL.md}) and section references (e.g., ``Section 2.1 Controls'') from the critique text using pattern matching against known artifact names and section header patterns. These references are attached to each \texttt{ReviewCritique} as \texttt{artifact\_ref} and \texttt{section\_ref} fields. Second, \textbf{revision framing}: instead of the generic ``Continue with: task'' prompt, revision iterations use structured framing:

\begin{lstlisting}
=== REVISION REQUEST (Iteration N) ===
You produced artifacts in the previous iteration.
The reviewer has identified specific issues that MUST be addressed.

=== REVIEWER FEEDBACK (Grade: B) ===

REQUIRED FIXES (must address):
1. [CRITICAL | stats | EVAL.md Section 3.2] p-value without effect size
2. [HIGH | reproducibility | PROTOCOL.md Section 2.1] Missing dataset URLs

SUGGESTED IMPROVEMENTS:
3. [MEDIUM | general] Consider cell-type decomposition

=== END FEEDBACK ===

TASK: Revise your artifacts to address ALL required fixes above.
For each fix, make the specific change in the referenced artifact.
Do NOT rewrite from scratch -- make targeted revisions.
\end{lstlisting}

\subsubsection*{Output cleaning pipeline}
LLM outputs frequently contain ``thinking traces''---narration about the model's intended actions (e.g., ``I will read the file\ldots'', ``Let me check the data\ldots'') that contaminate research artifacts. The output cleaning module removes these traces using regex-based line filtering:
\begin{itemize}
  \item Forward-looking narration: ``I will\ldots'', ``I'll\ldots'', ``Let me\ldots'', ``I need to\ldots'', ``I'm going to\ldots''.
  \item Tool-call narration: ``I will read/search/check/verify\ldots the\ldots''.
  \item Sequencing prefixes: ``First, I will\ldots'', ``Next, I'll\ldots''.
  \item Meta-commentary: ``The following is\ldots''.
\end{itemize}
The cleaner preserves code blocks (tracking \texttt{```} fences), markdown headers, and substantive past-tense narration (``I have completed the analysis\ldots''). Excessive blank lines left by removals are collapsed. Cleaning is applied immediately after adapter output, before any downstream consumer (artifact parser, feedback formatter, consensus merger).

\subsubsection*{Severity stratification and lens weighting}
Formatted feedback is stratified by severity---Critical and High critiques become \emph{required fixes} the executor must address, while Medium and below become \emph{suggested improvements}---so revision effort concentrates on what matters. Feedback is uniform across lenses by default; when a deployment trusts one lens more than another (for example, weighting the biological-plausibility lens for a tissue-specific study), an optional per-role weight biases the ranking so that lens's critiques appear earlier in the required-fixes list without changing which critiques are reported.

\subsection*{Verified execution}
By default an executor produces an analysis \emph{plan}; a plan that is never run cannot be checked. When \texttt{code\_execution\_enabled} is set, MI-Workbench extracts the fenced Python blocks from an executor artifact and runs each in an isolated subprocess---a separate \texttt{python\,-I} interpreter in a fresh temporary directory, with a wall-clock timeout, captured stdout/stderr, and an output-size cap---then appends a concise execution report to the feedback stream so the reviewer panel critiques executed results rather than an untested plan. Execution is opt-in and deliberately bounded: it verifies deterministic, self-contained snippets and is not a general sandbox for adversarial code, which would require an operating-system-level jail around the process. Even so, it closes the loop from proposed analysis to observed result and to critique of that result.

\subsection*{Knowledge extraction and claim management}

MI-Workbench includes a knowledge extraction pipeline that mines structured claims from research artifacts. \textbf{Claim detection:} claims are detected via pattern matching on phrases such as ``we found that\ldots'', ``results show\ldots'', ``AUROC = X'', and ``$p < 0.05$''. Detected claims are classified as \emph{empirical}, \emph{methodological}, \emph{interpretive}, or \emph{comparative}. \textbf{Uncertainty estimation:} each claim receives an uncertainty score $u \in [0, 1]$ (baseline 0.5) adjusted by strong evidence ($p < 0.001$: $u \leftarrow u - 0.2$), confidence intervals present ($u \leftarrow u - 0.1$), hedging language such as ``suggests'' or ``may'' ($u \leftarrow u + 0.1$), and large sample $n \geq 1000$ ($u \leftarrow u - 0.1$). \textbf{Falsification test generation:} for each claim type, the system auto-generates falsification suggestions---AUROC claims prompt stronger baselines (mutual information, variance-based features), layer-specific claims prompt split-sample validation, attention claims prompt residualization tests, and statistical claims prompt stringent multiple testing correction. \textbf{Claim graph:} claims are stored in a relational database with support for inter-claim relationships (supports, contradicts, extends) and evidence linking; a graph API enables visualization of the claim network, supporting identification of weakly-supported claims and contradictions.

Four git modes are supported: \texttt{none} (no version control), \texttt{commit\_per\_run} (single commit after run completion), \texttt{commit\_per\_iteration} (commit after each iteration), and \texttt{branch\_per\_run} (create a dedicated branch \texttt{run/\{run\_id\}}).

\subsubsection*{Reproducibility packages}
The \texttt{repropack} generator creates self-contained ZIP archives containing all artifacts from the run (organized by iteration); \texttt{run\_meta.json} with run configuration, timing, and cost; \texttt{prompts\_used.json} with resolved prompt templates; \texttt{environment.json} with Python version, installed packages, and OS details; \texttt{git\_state.json} with branch, commit hash, and dirty status; and auto-generated \texttt{dataset\_card.md}, \texttt{reproducibility\_checklist.md}, and \texttt{README.md}.

\subsection*{Key findings from automated analysis}
The platform autonomously identified three primary confounders explaining the attention--co-expression correlation. \textbf{(1) MLM objective confounder:} the executor agent correctly identified that Geneformer's masked language modeling objective incentivizes attending to co-expression cliques rather than causal regulators, because co-expressed genes are the most statistically powerful predictors of masked token identity. \textbf{(2) Rank-value encoding artifacts:} the system identified that Geneformer's rank-value tokenization creates an inductive bias where positional proximity in the sequence corresponds to expression magnitude similarity, producing false-positive attention between co-abundant genes (homophily) rather than regulatory links. \textbf{(3) Attention symmetry:} standard dot-product attention $\mathrm{softmax}(QK^\top)$ is inherently bidirectional unless the model learns distinct query/key projections; the executor noted that $A_{ij} \approx A_{ji}$ fails to capture the directional nature of gene regulation ($\mathrm{TF} \to \mathrm{Target}$).

\subsection*{Iterative refinement quality}
The structured feedback mechanism produced measurable quality improvements across iterations. In iteration~1, the executor produced an initial analysis with three confounders and a protocol outline with null hypotheses. In iteration~2, the reviewer identified missing controls---a cell-type composition confounder, an unspecified dataset, and missing BH-FDR correction details. In iteration~3, the executor revision added a within-cluster partial correlation control, specified the Genecorpus-30M human bone marrow subset, defined a mean rank baseline, and set a random seed. Critically, the revision iteration produced \emph{targeted changes} to the specific artifacts and sections referenced in the feedback, rather than rewriting from scratch---a direct result of the artifact-aware feedback mechanism.

\subsection*{Output quality assessment}
Post-hoc validation by domain experts confirmed that all three identified confounders are well-documented in the literature~\cite{pratapa2020benchmarking,theodoris2023transfer}; that the proposed null hypotheses ($H_0^1$: co-expression dominance, $H_0^2$: attention symmetry, $H_0^3$: degree bias) are scientifically appropriate; that statistical framework choices (AUPRC over AUROC for sparse networks, BH-FDR correction) reflect current best practices; and that the output contained no thinking traces (validated by comparison with pre-cleaning runs where traces contaminated 4/4 artifact files).

\subsection*{Orchestration evaluation}
The case study exercises one task; to characterise the orchestrator independently of any single question, we run a set of controlled experiments. Because a full LLM run is stochastic and costly, these use a deterministic mock adapter that emits, per reviewer lens, a fixed critique set with a small, controlled overlap; this isolates the \emph{mechanism} and its \emph{scaling} reproducibly, and we then corroborate the panel with a live Gemini backend. The mock experiments make no claim about research quality---that rests on the case study and the live corroboration.

\noindent\textbf{Does a panel add over a single reviewer?} We vary the panel size and measure how many distinct critiques survive merging (Table~\ref{table_ablation}). A single rigour reviewer surfaces three issues; adding the adversarial lens raises this to five and, because both lenses independently flag the missing-effect-size issue, agreement escalates it to Critical (grade F); adding the biological-plausibility lens raises coverage to seven. Coverage grows monotonically with panel size, and agreement upgrades severity exactly when independent lenses concur---evidence that a panel is not redundant with a single well-prompted reviewer.

\centering

\label{table_ablation}
\begin{tabular}{@{}lcccc@{}}

\textbf{Panel} & \textbf{Lenses} & \textbf{Distinct critiques} & \textbf{Multi-lens} & \textbf{Grade} \\ \hline

\end{table}

\noindent\textbf{Are the lenses complementary or redundant?} Treating each lens's critique set as a bag of issues, the pairwise Jaccard overlap is $0.20$ for rigour--adversarial and $0.00$ for both pairings involving biological plausibility; the union of all three lenses (seven distinct issues) is nearly the sum of their individual counts (eight), so the lenses overlap little and the biology lens in particular contributes issues the others never raise. The roles are complementary by construction, not duplicative.

\noindent\textbf{Convergence.} Over 20 independent runs of the consensus loop, every run terminated by convergence rather than the iteration ceiling, at a median of 8 iterations, each time via the grade-stabilization signal. The loop reliably detects when further iteration is unproductive.

\noindent\textbf{Load and scalability.} Although each run is coordinated centrally, independent runs execute concurrently. Driving 1 to 20 concurrent runs through the orchestrator (Fig~\ref{fig2}), aggregate throughput rises from about 110 to 376 iterations/s while p95 per-run latency grows sub-proportionally (from 55\,ms to 314\,ms at $20\times$ concurrency), and a database-integrity check passes after every level. The centralized coordinator therefore scales across concurrent investigations, with tail latency degrading gracefully rather than collapsing.

\end{figure}

\noindent\textbf{Live-backend corroboration.} To confirm the wired panel behaves as characterised with a real model, we ran the three-lens panel once over a fixed Geneformer analysis artifact using the Gemini backend. All three lenses returned; the rigour lens alone produced 12 critiques, and the full panel produced 23 distinct merged critiques---roughly double the coverage---consistent with the ablation. Notably, verbatim Jaccard deduplication rarely merged critiques across lenses on free-text output (the lenses phrase overlapping concerns differently), which both underlines the coverage benefit of a panel and motivates semantic, rather than lexical, deduplication as a refinement.

\section*{Discussion and conclusion}

MI-Workbench shows that a centrally orchestrated team of LLM agents can carry out mechanistic-interpretability investigations that are rigorous, reproducible, and inspectable. The evaluation supports its core design choices: a reviewer panel surfaces strictly more, and complementary, critiques than a single reviewer; agreement between lenses escalates severity where it should; the loop reliably detects convergence; and the centralized coordinator scales across concurrent runs with graceful tail-latency growth. The provider-agnostic design insulates workflows from any one vendor, and the accompanying test suite exercises the orchestration, consensus, feedback, and execution paths.

We deliberately trade agent autonomy for a deterministic, auditable control flow, which is the right trade for automated scientific critique: a run's sequence of agent calls follows from its workflow graph, every artifact and prompt is persisted, and any run can be repackaged for independent reproduction. The domain specificity lives in swappable prompts and configurable reviewer lenses rather than in the engine, so the same coordinator drives other domains and other panel compositions; the evaluation experiments are themselves task-independent evidence of this separation.

Several limitations remain. Verified execution is opt-in and intentionally bounded---it runs deterministic, self-contained snippets in an isolated subprocess but is not a hardened sandbox for adversarial code, which would require an operating-system-level jail. Critique deduplication is lexical (word-level Jaccard); as the live-backend corroboration shows, real reviewers phrase overlapping concerns differently, so semantic deduplication via embeddings would merge and escalate agreement more faithfully and would also sharpen the convergence signal. Cross-provider cost accounting depends on adapter-level reporting and is not yet standardized. Finally, coordination is centralized: this is a feature for reproducibility but caps single-run parallelism at the reviewer panel, and there is no mechanism for mid-loop human redirection beyond the follow-up approval policy. Natural extensions include semantic merging and convergence, multi-model ensemble execution that runs a task across several backends and compares outputs, integration with laboratory-automation systems for wet-lab validation, and richer human-in-the-loop control.

In sum, MI-Workbench contributes a graph-based workflow DSL, a concurrent consensus-review mechanism with a defined aggregation and gating semantics, artifact-aware structured feedback, sandboxed verified execution, and a provider-agnostic architecture, evaluated with both controlled orchestration experiments and a live-backend case study. It provides a foundation for scaling mechanistic interpretability of biological foundation models beyond the capacity of individual researchers.
